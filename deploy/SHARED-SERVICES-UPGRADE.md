# 共享服务版本升级

适用于已有的 Sub2API Docker / Compose 部署。不要新建一套数据库或重新初始化安装。

## 升级前

1. 记录当前应用镜像完整名称和 digest，保存现有 Compose、环境变量配置及挂载信息。配置中可能包含密码，不要贴到公开仓库。
2. 为现有 PostgreSQL 做可恢复备份，确认备份文件非空、能列出内容；同时备份应用 `/app/data` 对应的宿主机目录。Redis 的现有持久化配置和挂载也保留。
3. 若无法确认数据库和 `/app/data` 已持久化到容器外，先完成持久化和备份，再重建应用容器。

## 1Panel 中更新已有部署

在原有应用容器或原有编排中，只替换 Sub2API 的镜像为正式版 `ghcr.io/tezicn/sub2api:0.2.26`。`latest` 也指向最新正式发布；使用明确的版本标签便于确认及回退。

保留原项目名、数据库地址/库名/用户名/密码、Redis 配置、所有环境变量、端口、网络、卷及挂载路径。拉取镜像后仅重建 Sub2API 应用服务；PostgreSQL 和 Redis 继续使用原服务及原数据。

如果通过 Compose 命令更新，在原 Compose 目录、使用原环境文件和项目名，修改应用 `image` 后执行下列命令。先用 `docker compose config --services` 确认应用服务名；示例中的 `sub2api` 必须与现有服务名一致。

```bash
docker compose pull sub2api
docker compose up -d --no-deps sub2api
docker compose logs --tail=100 sub2api
```

不要执行 `docker compose down -v`，不要删除数据库卷、清空数据目录、卸载并清除原应用数据或覆盖原 `.env`。

## GitHub 在线更新

从 0.2.26 开始，页面的更新检查、下载和回退都使用 `TeZicn/Sub2API` 的 GitHub Releases，正式发布同时提供各平台安装包和 `checksums.txt`。仅推送源代码不会触发在线更新，必须发布版本号递增的正式 Release。

旧版本中写死的更新源是 `Wei-Shaw/sub2api`，此前的 `shared-<提交号>` 试用镜像也仍使用旧更新源。因此第一次请按上面步骤替换应用镜像到 0.2.26；之后管理员可以在版本菜单中选择“检查更新 → 立即更新 → 重启服务”。容器需配置 `restart: always` 或 `unless-stopped`，否则程序退出后应在 1Panel 手动启动原容器。

在线更新替换当前容器里的程序，不清空数据库和 `/app/data`。容器普通重启保留该程序；删除并重建容器会重新使用镜像内的版本。以后在 1Panel 重建或迁移容器前，要同步使用对应的新版本镜像（或拉取最新 `latest`），并保留原挂载和环境变量。在线回退到不支持共享服务的 0.2.25 前，也必须先按下面的回退说明停用共享 Key。

## 验证及回退

启动时自动执行新增的 253–257 迁移：新增共享发布、成员表、活跃时间、软删除标记、模型展示列表，以及 API 密钥的可空关联字段。001–252 迁移不改写；本次新迁移不重置用户、余额、旧 Key 和历史记录。

确认应用 `/health` 成功，原管理员可以登录，已有用户、余额、Key 和历史用量可见后，再创建一个小额度或短时间的共享服务进行测试。服务结束后检查共享 Key 失效、普通 Key 仍可正常使用。

遇到问题时，先在新版本中下架已发布的共享服务并确认关联 Key 已停用，再把应用镜像切回升级前记录的版本并仅重建应用服务，保留数据库和挂载。旧版本不提供共享服务；如果新版本已经无法启动，应保持应用停机，先处理共享 Key 的禁用再回退。若需要恢复数据库，应先停止应用写入并保存当前数据，再按备份恢复流程操作，不能直接覆盖仍在运行的数据库。

## 额度边界

共享请求不扣个人余额；额度模式按项目模型价格目录及发布配置倍率累计共享消耗。结算具有去重保护。达到限额后拒绝新请求，已经放行的请求可完成，因此最终消耗可能略高于设置的阈值。时间模式和额度模式互斥。

## 活跃用户与份额

创建 Key 只获得临时使用资格，不占用活跃份额。真实请求申请执行时记录用户活动，同一账号的多把 Key 只计一人；5 分钟无请求则自动退出名单和均分，再次请求重新参与。余数按本次进入活跃名单的顺序分配，并受个人上限和共享总上限共同限制。人数达到共享总上限时，新用户的请求使用现有等待及限流机制，已有 Key 不会被删除或停用。页面每 15 秒刷新一次活跃名单，因此显示可能有最多约 15 秒延迟。

## 管理与权限

管理端新建、编辑使用配置弹窗。“开放模型”由管理员逐项填写，换行或逗号分隔；它只控制卡片展示，实际请求仍由绑定分组的模型权限决定。升级已有共享服务时此字段为空，需要在编辑弹窗补充展示名称。

删除共享服务会移除管理列表和用户列表中的条目，撤销关联共享 Key，并释放分组绑定。数据库保留发布、成员、Key、用量和账单历史，删除前已放行的请求仍可正常结算；重新绑定同一分组会建立新的发布和资格，不恢复旧 Key。

共享资格只适用于共享服务入口创建的 Key，不会把专属分组加入普通“API 密钥”的可选列表，普通创建接口也不会借用共享资格。删除 Key 后需要从共享服务卡片重新创建；用户原本已有的正式分组授权不受影响。
