# 共享服务版本升级

适用于已有的 Sub2API Docker / Compose 部署。不要新建一套数据库或重新初始化安装。

## 升级前

1. 记录当前应用镜像完整名称和 digest，保存现有 Compose、环境变量配置及挂载信息。配置中可能包含密码，不要贴到公开仓库。
2. 为现有 PostgreSQL 做可恢复备份，确认备份文件非空、能列出内容；同时备份应用 `/app/data` 对应的宿主机目录。Redis 的现有持久化配置和挂载也保留。
3. 若无法确认数据库和 `/app/data` 已持久化到容器外，先完成持久化和备份，再重建应用容器。

## 1Panel 中更新已有部署

在原有应用容器或原有编排中，只替换 Sub2API 的镜像为本次构建提供的 `ghcr.io/tezicn/sub2api:shared-<完整提交号>`。

保留原项目名、数据库地址/库名/用户名/密码、Redis 配置、所有环境变量、端口、网络、卷及挂载路径。拉取镜像后仅重建 Sub2API 应用服务；PostgreSQL 和 Redis 继续使用原服务及原数据。

如果通过 Compose 命令更新，在原 Compose 目录、使用原环境文件和项目名，修改应用 `image` 后执行下列命令。先用 `docker compose config --services` 确认应用服务名；示例中的 `sub2api` 必须与现有服务名一致。

```bash
docker compose pull sub2api
docker compose up -d --no-deps sub2api
docker compose logs --tail=100 sub2api
```

不要执行 `docker compose down -v`，不要删除数据库卷、清空数据目录、卸载并清除原应用数据或覆盖原 `.env`。

## 验证及回退

启动时自动执行新增的 253、254 迁移：新增共享发布、成员表，以及 API 密钥的可空关联字段。001–252 迁移不改写；本次新迁移不重置用户、余额、旧 Key 和历史记录。

确认应用 `/health` 成功，原管理员可以登录，已有用户、余额、Key 和历史用量可见后，再创建一个小额度或短时间的共享服务进行测试。服务结束后检查共享 Key 失效、普通 Key 仍可正常使用。

遇到问题时，先在新版本中下架已发布的共享服务并确认关联 Key 已停用，再把应用镜像切回升级前记录的版本并仅重建应用服务，保留数据库和挂载。旧版本不提供共享服务；如果新版本已经无法启动，应保持应用停机，先处理共享 Key 的禁用再回退。若需要恢复数据库，应先停止应用写入并保存当前数据，再按备份恢复流程操作，不能直接覆盖仍在运行的数据库。

## 额度边界

共享请求不扣个人余额；额度模式按项目模型价格目录及发布配置倍率累计共享消耗。结算具有去重保护。达到限额后拒绝新请求，已经放行的请求可完成，因此最终消耗可能略高于设置的阈值。时间模式和额度模式互斥。
